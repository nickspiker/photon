**v1 FLEET MEMBERSHIP CHAIN SHIPPED + DEPLOYED 2026-06-30** (supersedes the v0 Merkle-root keyring described below; v0 client `keyring.rs` DELETED, worker root model removed). The confirmed signed-list model is now the live implementation:
- `photon/src/network/fgtw/fleet.rs` — `MembershipBlob` = ordered `FleetOp` chain {handle_proof, prev_hash, kind(Genesis/Add/Remove), device_pubkey, eagle_time, signer_pubkey, sigs}. Sigs are an **egg-list** (`[(scheme,sig)]`, "every egg must verify", Ed25519=scheme 0, PQ additive). `fold()` IS the auth rule: valid sig + hash-chain link + signer-was-a-member-before-this-op (genesis self-signs into empty set); handle_proof bound into every op (anti chain-transplant). Builders genesis/add/remove; VSF wire = section "fleet", repeated positional "op" multi-value field [hP,hb,u,ke,e6,ke, then (u,ge) egg pairs]. Client oracle (stateless, fetch-then-sign): `fetch()`/`publish()`/`ensure_member()` (first-come genesis when none). 10 tests (incl. known-answer parity vector).
- `fgtw/src/fleet.rs` — verifier mirror (parse+fold, no builders, sync dalek), kept byte-identical via the shared known-answer test. `handle_fleet_op` accepts a posted chain only if it folds clean AND forward-extends the stored chain (optimistic concurrency); `handle_fleet_get` serves it. **GENESIS OWNERSHIP CLOSED 2026-06-30 (deployed 15795c71; photon eaac6a4 / fgtw d4a00bf):**
- **Genesis is identity-signed.** The genesis op carries `identity_pubkey = Ed25519(identity_seed)` + `identity_sig` over signing_bytes. identity_pubkey is folded INTO signing_bytes (device sig commits to it, can't be swapped) and identity_sig into chain_hash; genesis-only via kind-gated wire layout (ke,ge after signer, before egg pairs). `fold()` REQUIRES a valid binding on genesis (`BadIdentityBinding`) and rejects one on any other op (`StrayIdentityBinding`). `MembershipBlob::genesis_identity_matches(seed)` lets a contact who knows the handle confirm a friend's fleet is genuinely theirs.
- **Genesis-at-attest:** `fleet::ensure_member` runs inside the announce flow (bootstrap.rs, spawn_blocking bridge) BEFORE the announce send, so a fresh identity claims its fleet before handle_proof is ever published.
- **Announce GATED:** fgtw handle_announce now rejects any device not in `fleet_members(handle_proof)` — the ungated double-registration is closed. Storage key bumped `fleet/` → `fleet/v1/` (old-format chains orphaned, not bricking).
- **Residual (the honest limit):** FGTW still can't cheaply VERIFY ownership — `handle_proof = handle_proof(identity_seed)` is a ~1s memory-hard OWF with no cheap-verify, and identity_seed is secret, so a squatter CAN still first-come-genesis with a FAKE identity_pubkey and FGTW accepts it (peers who know the handle detect the fake via genesis_identity_matches; the operational genesis-at-attest shrinks the window). True server-verifiable ownership = the deferred ZK/accumulator egg. The chain closes: genesis→identity, each later op→previous via hash + prior-member.

**v0 SHIPPED + deployed 2026-06-29** (photon a1db59f, fgtw dabcc87, ihi 0.0.48 published). What's built, and the key divergence from the patent-ideal below:

- FGTW `handle_keyring_op` + `keyring/<handle_proof_b64>` = {kr_ver, root, root_ts} (no list/count); avatar gate = Merkle inclusion of the signing device's leaf vs root; announce rewritten multi-device (rows keyed (handle, device), one-handle-one-device checks DELETED). blob stays per-device. **VERIFIED single-device end-to-end live on fgtw.org (Nick).**

**KEY DIVERGENCE from the patent-ideal (decided under implementation pressure):** v0 uses **pubkey-based** leaves `spaghettify(DEVICE ‖ device_pubkey ‖ handle_proof)` + a **Merkle root**, NOT the patent's secret-based lossy-binding-with-no-list. Why: FGTW (the verifier, stores only the root) must RECOMPUTE the leaf from the signing pubkey to bind signer↔leaf — a secret-based leaf is unverifiable-by-recompute and a bare inclusion proof doesn't bind it to the signer. So pubkey-based was forced for "FGTW verifies against only the root." Cost: someone who knows your handle AND a device pubkey can test that device's membership (modest). Unguessable secret-based + no-list returns later with a ZK/accumulator egg. handle_proof (public) is the identity-binding component, NOT identity_seed (kept off-wire).

**THE GAP — multi-device is NOT solved yet (the actual motivating bug).** v0 wires only single-device genesis: a 2nd device (phone) does genesis→rejected(exists), proves against its OWN solo tree, FGTW checks against the 1st device's root → **403 "writer not in keyring"**.

**FLEET MODEL CONFIRMED 2026-06-30 (supersedes v0's client-persistence + per-device-announce approach):**
- **The device is a blind, stateless signing oracle: it knows ONLY its own private key (+ the handle the user provides) and CANNOT persist fleet state. State persistence is the NETWORK's job.** This is the load-bearing constraint — it forecloses the v0 client design.
- **The fleet record lives WHOLLY on the network as ONE object per identity:** the SET of device pubkeys + a CHAIN where every update is signed by a device that was valid in the PREVIOUS state ("only the previous-known-good can update"). The signed chain IS the provenance peers replay to trust a friend's fleet change. ("single multi-sig entry, not two rows.")
- **Devices fetch-then-sign:** on use, a device fetches the fleet record, finds its own pubkey, signs an update; it holds NO local leaf-list, NO "genesis_seen", NO root cache. v0's `solo_leaves` / `genesis_seen` / local persistence is the WRONG shape and must be redesigned to the oracle model.
- **Count is visible to FGTW for now** — unavoidable: a stateless device can't hold the leaf-set, so the network (FGTW) must, and to verify an update-signer is a member FGTW holds the pubkeys. Hiding count from FGTW needs a cryptographic accumulator (constant-size, O(1) witness, the deferred egg) AND something network-side to issue witnesses. **Count-hiding is DEFERRED to that accumulator egg, NOT a v0-multi concern.**
- **The intended count-hiding upgrade is MODULUS-based** (user's recurring instinct, stated twice — "does modulus help?" then "it has something to do with modulus"). That's exactly right: RSA / class-group accumulators are membership-by-modular-exponentiation against one constant-size value — "a list folded into one number you can test against without seeing it." It LAYERS over the signed device-key set without changing membership logic. The signed-list-of-keys is confirmed as the floor (forced by: only-real-secret-is-the-silicon-key since the handle is disclosable; no shared secret; stateless devices). "Roll with the list" decided 2026-06-30; the accumulator is the dream-upgrade, not a redesign.
- **The two wrong things in shipped v0 to fix:** (1) the **ungated `announce`/`peers.vsf`** (anyone who knows handle_proof can self-announce a device row → the spoofable "double registration") must be subsumed/gated by the fleet record; (2) the keyring object stores only a bare ROOT HASH — it must instead store the **signed, chained device-pubkey set** (provenance, shareable to peers), since count-hiding (the only reason for the bare root) is deferred anyway.
- Still relates to [[project_rarangi_messages_fleet]] ("fleet = a conversation") + the deferred "fleet private-key collection via CLUTCH" (a fleet CLUTCH for shared key material is a SEPARATE later layer; the device-set chain above does NOT need it — membership is by pubkey-in-the-signed-set, verified by signature, no shared secret required). The `add`/`remove` primitives partly exist; the redesign is: network-held signed chain + stateless fetch-then-sign client + gate the announce.

**The patent's model (use THIS, supersedes my earlier hand-rolled signed-log sketch):**
- Device-set lives in the WEB (FGTW→peers per [[project_peers_are_fgtw]]), not on-device.
- Each device binds via `binding_id = one_way_fn(device_secret ‖ handle)` (claim `binding`); the OWF is **provably lossy** (claim `lossy`, ~1−1/e reachable).
- **Bindings are MUTUALLY UNLINKABLE** — "neither reveals or has any relation to the other." So device COUNT is hidden by construction: **no list, no Merkle, no accumulator, no multi-sig, no RSA/modulus.** This is the answer to the device-count-vs-multisig privacy question (user asked "does modulus help? RSA?" — no; the lossy OWF is the mechanism).
- Membership proved by a **device-secret-signed attestation** vs a fresh challenge (claim `machine`, anti-replay); verifier never sees the secret.
- Genesis = first device claims handle (first-come). Remove = **delete binding from the user-controlled registry** (claim `bindingrevoke`); revocation sticks because the web won't HONOR the deleted binding (not the device forgetting).
- **TWO ORTHOGONAL relationships — NOT "one device one handle" (that misreading forbids the patent's own Fig 3):** (a) one handle → MANY devices = the fleet, UNBOUNDED (claim `cardinality`); (b) one device → many handles = shared/lent device, ALLOWED but owner-gated + off by default (claim `binding`/Fig 3, "plurality-of-bindings... by the owner's grant"). The web invariant at patent line 741-742 is **anti-theft** (a FOREIGN/unauthorized handle can't DISPLACE your device's owner-of-record binding without your authorization), NOT a cardinality cap. (I wrongly compressed it to "one-device-one-handle" 2026-06-29; corrected.)
- Tiered device authority (claim `devauthority`): asserting ≠ enroll/revoke privilege. Remote revoke by a mgmt-privileged device, or custodian threshold if that device is the lost one. Every assertion broadcast to the whole fleet by default (claim `assertionalert` = the "loud UI" requirement, already a claim).

**The lossy OWF IS built** (corrected 2026-06-29 — see [[reference_ihi_primitives]]): it is `ihi::chaos_amp` / `ihi::spaghettify`, the 32-op data-dependent lossy ALU, bit-exact with PIPE silicon. So the **information-theoretic device-count unlinkability is available TODAY** — derive the binding as `spaghettify(device_secret ‖ handle)`, no Merkle/accumulator/multisig, no "ship BLAKE3 now version-bump later" compromise. (I twice mis-read `ihi::handle_proof` — the memory-hard PoW / anti-squat cost, a DIFFERENT function — as "the lossy OWF, unimplemented." Both are built; handle_proof = cost half, spaghettify/chaos_amp = lossy half.)

**Auth rule the user picked (2026-06-29): any single member holding the enroll/revoke privilege may Add and Remove** — reconciled with the patent's tiered-privilege + delete-from-registry revocation.
