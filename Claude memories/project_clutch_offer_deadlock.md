CLUTCH ceremonies park in Pending whenever an offer transfer dies, because offer sending was one-shot + pong-driven. Generations of this bug:

**2026-06-26/28 (Nick↔Robert, all fixed on main):** (1) PT inbound drain keyed by peer address only — concurrent offer/KEM streams from one peer collided and the offer got dropped (918552f, stream-scoped drain). (2) Dual-stack [::] socket silently drops plain-V4 sends — chat + ClutchComplete used raw race_addrs V4 (e39e878, map to ::ffff: in async udp::send). (3) AwaitingProof recovery: duplicate proof re-arms the Complete side's resend budget; AwaitingProof side tops its budget each ping while peer online (6325cd9).

**2026-07-19 Nick↔Mary (FIXED @ 7d5e356):** PT's stale cap `retries > 10` counted LIFETIME timeout rounds and `rtt.update()` recomputes RTO from SRTT on every ACK (wiping `backoff()`), so a 256-packet blast into a cellular path (RTT ≈ RTO) bumped retries every tick WHILE ACKs streamed in — both sides' 549KB offers self-killed ~1s after locking a WORKING path (after ~12s wasted racing the peer's dead carrier-NAT 10.x LAN record + TCP fallback; is_stale's two conditions were indistinguishable in the log). With no pongs flowing (Mary sat TIMEOUT 20 min while punch keepalives validated her IPv6), no pong-gated recovery could ever fire. Fixes: PT `retries` = consecutive-no-progress (reset on ACK progress + on SPEC-ACK lock); parked-offer re-fire on the path-validated EDGE (Pending + offer sent + peer slot offer absent, friends only) via `resend_clutch_offer(idx)`; ping-cycle safety net (`Contact::clutch_offer_stall_cycles`, re-fire every 6 validated-path cycles); presence pings also target `validated_path` when it matches neither LAN nor registry ip; the 3 silent pong-drop gates in status.rs now log their reason.

Diagnosis tips that paid off: `photonlog --pull --handle <peer>` (submitted logs are DESTROYED by a worker nuke — check fgtw.org/admin/activity for a log-put row first); the PT: lines tell the whole transfer story; "TRAVERSE: ACK … path validated" every cycle without the one-shot "path validated to <contact>" line ≈ keepalives refreshing an already-recorded path.

STILL OPEN: why a peer's pongs never arrive at another (probes/acks/SPEC/DATA all arrive and both gates are identical — the new torches will answer it in the next submitted log); the phone running the pre-fix build keeps self-killing its outbound offers until it updates.

**2026-07-23 relay-torch-race (FIXED @ 9a9d2d5):** the clutch offer_provenance was derived from the offer PUBKEYS (a drift; CeremonyId::derive's own doc says the design was BLAKE3(sender_pubkey || timestamp)). Key-based provenance made the clutch ROTATE — the torch-on-mismatch re-keyed → new pubkeys → new provenance → new ceremony_id, and over the relay both sides torched on the same transient faster than the RTT, staying one generation apart forever (the clutch-toggling). Fix (two-strands-sorted model, per user): each party derives provenance from (its device key + its PINNED send-time = Contact::clutch_round_started), stamped into the offer's creation_time so the receiver mirrors it via `clutch_offer_provenance()` in clutch.rs; distinct send-times → distinct provenances → CeremonyId::derive SORTS them → identical ceremony_id both sides. Keys stay randomly seeded (NTRU/HQC via pqcrypto CAN'T be seeded — internal PQClean randombytes, no RNG param). The clutch does NOT rotate: both torch sites removed, a mismatch keeps every pinned input and stays AwaitingProof (deterministic stable inputs converge; a surviving mismatch = real bug, logged not spiralled). Flag-day: new provenance domain `PHOTON_CLUTCH_OFFER_PROV_v2`, both peers must run 0.41.x+ with this. test `clutch_offer_provenance_sorts_to_same_ceremony_id`. E2E over relay pending a fresh log.

**2026-07-23 relay-torch-race (SUPERSEDED — was OPEN, DIAGNOSED):** with the pipe data plane working (offer/KEM/proof all flow over the relay), a pure-RELAY ceremony PERPETUALLY re-keys and never seals — the "clutch toggling" symptom. Root: torch-on-PROOF-MISMATCH (photon_app.rs ~13018 and ~9809) fully resets the round (fresh keypairs/offer/provenance) on ANY same-round egg mismatch. Over the relay's multi-second RTT, BOTH sides torch independently on each mismatch, and re-keying is faster than the round-trip — so each side is always computing eggs from its CURRENT generation while responding to the OTHER's PREVIOUS one. They stay permanently ~1 generation apart → perpetual mismatch → perpetual torch (observed 11 torches / 40 keygens in minutes). NOT a crypto bug: clutch.rs is address-independent (no sender_addr/RELAY_ADDR), the KEM target_hqc always matches the current offer, eggs ingredients are all canonically sorted+symmetric — the mismatch is a cross-side TEMPORAL generation skew, not diverged transcripts. Direct-path ceremonies seal fine because low latency lets a round complete before the next torch. Ruled out: truncation residue (mismatch persists after both on the 64KB-buffer-fix build 0.41.7+). CANDIDATE FIXES: (1) deterministic per-round keypair = KDF(sorted party ids, round id) so re-keying can't create a generation the peer must chase — the root cure, touches keygen; (2) don't torch when reached_via_relay — treat a mismatch as stale-generation-crossing, wait for the round to settle. Both untested; direct path works so don't regress it.
