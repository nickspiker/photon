## Messaging / protocol

- **Friend consent gate**: `on_search_result(Found)` auto-adds + auto-CLUTCHes — search IS befriend. Needs a pending/accept state so a stranger can't complete a ceremony + deliver a message just because someone searched a handle (observed live 2026-07-16: "an attacker just got this message"). Mutual-consent design notes in the peers-are-fgtw plan.
- **CLUTCH ownership evolution (§4.2)** (design, 2026-07-31 — from the live dozing-owner stall: peer_m's re-key waited on Nick's sleeping phone while peer_b parked): two stages. **A — transferable claim (do first)**: ownership becomes a LEASE — any awake sibling may claim an unclaimed-or-expired ceremony; claims carry (epoch, device_pubkey) monotonic tiebreak and ride the fstate hub push (~150ms fleet-wide), owner renews while alive, ~30s silence → any sibling re-claims and drives. Friend side already accepts any folded member's offers; no wire change; deletes the dozing-owner stall. **B — race-and-converge (after the primary registry lands)**: no ownership; ceremonies are device-pair-scoped (ceremony_id already derives from offer provenances); ANY pair may run one; convergence at ADOPTION: both fleets saw every competing ceremony_id, so both independently keep min(ceremony_id) and discard the rest — late/duplicate completions are no-ops by construction. Cost: a message can ride a losing chain in the near-simultaneous window; the fork detector heals it, but that makes fork-healing a NORMAL mechanism rather than an emergency one — decide that deliberately.
- **CLUTCH sibling-race**: a peer's sibling device initiating CLUTCH before we fold it into the contact's fleet gets rejected by the PT gate and gives up before the fold lands (~20 min stall observed). Fix = re-initiate after fold, or queue the offer until the fold verdict.
- **Blind ops (private identity S) E2E**: the party-id token seam is fixed (2026-07-16, tokens now derive from party ids on both ends) but the full S lifecycle (probe → generate → deposit → ack → recover) hasn't run E2E across real devices since.
- **Fleet message sync E2E**: phase-2 sibling history sync + live push shipped @ c6d6285; needs the 2-device live run (send on A, watch B; fresh-join backfill; delivered-tick propagation).
- **NAT traversal relay tier**: reflexive/punch/keepalive exist, but symmetric↔symmetric NAT pairs have NO fallback path. Needs a relay tier (friend-fleet devices as relays fits the peers-are-fgtw direction).
- **Chain-advance desync (parked)**: one observed case of ratchet divergence by msg 2 after a Complete (garbage plaintext); salt-from-last_plaintext a prime suspect. Re-test post party-id fixes before digging.

## One-directional-path doctrine (2026-07-31)

Three independent subsystems died the same death in one day of live logs: a VALIDATED or plausible direct path whose REVERSE direction silently drops — blind srv answers (probe expired forever while the peer served every 15s), message ACKs (direct ack lost → sender retransmit-timeout → duplicate → only the re-ACK's relay copy landed), history page responses (2,322 re-requests in one session while every request arrived fine). Doctrine adopted: **small idempotent response frames ALWAYS carry their relay copy alongside any direct leg** — blind (all four frame types), ACKs (both sites), history page serves (one-device relay_to). Validation proves OUR probes round-trip, never that the reverse delivers. Suspect the same mechanism in punch-probe replies (why validated paths are scarce) — next traversal investigation.

## Transport / NAT traversal — direct-path hardening

Ordered; land + 2-device-test each before the next, relay tier (above) is last. Diagnosed from peer A (cellular carrier behind CGNAT) ↔ peer B (fiber) logs: peer A never held peer B's public candidate + no keepalive → one-sided punch (peer B 209 probes, peer A 0). DONE on branch `transport-resilience`: **validated-path keepalive** — clamp the presence sweep to 20s while any validated path is held so CGNAT mappings don't die mid-session (`photon_app.rs` `presence_ping_interval` + `VALIDATED_PATH_KEEPALIVE`, @5f5bfdc); **punch-on-address-learned** — `refresh_contact_addrs_from_peers` fires an immediate sweep when a peer addr is learned/changed, so the late-fetch side punches at once instead of sitting silent (@b5cc6c2).

- ~~**Address discovery via peer gossip (T0)**~~ LARGELY LANDED 2026-07-31: the seed now serves a per-record phonebook registry (`pb_put`/`pb_get`, fgtw-bootstrap; records self-signed, monotonic-timestamp guarded) and clients both publish their quorum-corroborated reflexive address to it and resolve stalled contacts' devices from it (`phonebook_client.rs`, `resolve_stalled_addresses_from_seed` — asked LAST, after gossiping every reachable peer). Verified live: resolve → endpoints → punch fired on both peer_a and peer_b the same day. Still open from the original write-up: sibling-gossip as the middle tier (ask a reachable sibling before the seed), and retiring the 15s full-resume pulse (it re-runs the whole attest; should be announce-only or doorbell-driven). Original ticket for reference below.
- **(superseded T0 text)**: address discovery is 100% dependent on a device's OWN fgtw.org reachability. On flaky cellular that strands everything downstream — observed peer A↔peer B: peer A's fgtw failed 4/7 (`contact fleet refresh failed for <dev>: No connection to FGTW`), so it never learned peer B's address, the CLUTCH offer was built + `Stored local offer` but NEVER sent, and the ceremony looped Pending re-keygenning every ~1-2 min. Meanwhile peer A had a healthy keepalive-held v6 path to its own sibling `<dev>` — which can reach fgtw AND knows peer B's address. Fix: on an fgtw fetch/refresh failure, ask a reachable sibling/friend for the peer's `PeerRecord` over the working path (`PhonebookRequest`/`Response` already carry self-signed, relay-verifiable records — the plumbing half-exists). Removes the single-point dependency on a device's own uplink. Higher priority than T1.3/T3/T2 below: those all assume you already HAVE the peer's address; this is why you often don't. Stopgap: aggressive fgtw retry (every ~3-5s) while a ceremony is Pending, to catch a working window sooner than the current ~1-2min cycle. NOTE: the fire-on-address-learned fix (@b5cc6c2) can't help here — it needs a learned event that a failing fetch never produces.
- **TCP as a direct path (T1.3)**: `tcp.rs` has NO inbound accept today — TCP is only a whole-payload PT fallback to an already-known UDP address (`pt/mod.rs` ~554). Add (a) an inbound TCP listener on `PHOTON_PORT` handing framed VSF to the same `status.rs` receiver pipeline, and (b) a parallel TCP-connect to a peer's public/forwarded candidate raced alongside the UDP punch. Wins: UDP-blocked networks (corporate / some mobile), and TCP-direct to a forwarded host "just works" (the port-forward / RustDesk-host case). Test: UDP-blocked client reaches a forwarded host over TCP.
- **IPv6 as a first-class direct path (T3)**: `gather.rs` prioritizes `HostV6` (100) but "full local-interface enumeration deferred (P2)" and the announce may not carry a global v6. Add local global-v6 enumeration + carry it in the FGTW announce (worker parse is already generic) so a v6-capable pair connects direct over v6 — NO NAT, no punch. Biggest single win for a cellular peer if its carrier is v6 (bypasses CGNAT entirely). Test: two v6 hosts connect with zero punch; verify a cellular device gets a global v6.
- **Server-coordinated simultaneous-open (T2)**: today each side punches on its own ping cadence with no two-sided timing, and the WS channel (`wss://fgtw.org/ws`) is broadcast-only. Add targeted WS delivery in the worker (per-connection subscription by device_pubkey / handle_proof) + a "punch-request" msg: A deposits "punch B, here are my candidates, window ≈ T" → worker pushes to B → B punches back at once. Breaks the chicken-and-egg AND gives tight timing for restrictive (non-symmetric) NATs. **NEEDS WORKER DEPLOY** (`fgtw-bootstrap`, user-run). Test: cold pair (neither pre-punched) connects on first attempt.
- Then **NAT traversal relay tier** (see Messaging/protocol above): the symmetric↔symmetric / double-CGNAT case (two cellular peers) that direct can never reach.
